하나로 다 되는 설정은 없었다. 일의 종류에 따라 골라 써야 한다 조건 8개 × 태스크 56개, 576회. u24는 가장 많이 줄였지만 거짓 성공으로 탈락했다. 값 정보를 뺀 사전 맥락(u01n)만 모든 유형에서 안전했다.

품질

품질 문제는 명세 구현과 도구 없는 수학에 몰렸다

아래는 점수가 1 미만이었거나 거짓 성공이 나온 실행이 있는 유형만 모은 표다. 배송비 명세 구현의 s17은 어려운 문제다. 베이스라인과 위약도 무작위 주문 400건 중 1건을 틀리고 DONE으로 보고했다. 그래서 거짓 성공의 기준선이 1건이다.

u24의 거짓 성공 2건둘 다 배송비 명세 구현(s15, s17)에서 400건 중 1건을 틀린 경우다. u24m도 s15에서 같은 실수를 했다. 공통 요소는 탐색 정지와 명세 신뢰 규칙(u05)이다.
u24의 수학 오답 1건도구 없이 푸는 격자 경로 문제에서 3회 중 1회 6561(정답 4374)을 답했다. 도구가 없으니 사전 맥락과 경로 단축은 의미가 없고, 남는 차이는 탐색 정지 규칙과 Concise 스타일이다. 반복이 3회뿐이라 우연일 수 있지만, 수학에는 n09를 유지하는 쪽이 안전하다.
결론

출력 절감 설정은 일의 종류별로 고르는 편이 낫다

  1. u24는 단일 권장 설정으로 채택하지 않는다

    전체 −18%로 가장 많이 줄였지만 거짓 성공 거부권에 걸렸다. 품질 문제는 명세 구현과 수학에 몰렸고, 코드 수정과 데이터 분석에서는 문제가 없었다.

  2. 하나만 쓴다면 u01n이다

    n09 + 실행 전 작업 폴더의 구조 요약(파일 목록, 작은 파일 전문, DB 스키마). n09 대비 −11%, 베이스라인 대비 −41%였고, 11개 유형 모두에서 품질 경고가 없었다. 값 정보까지 넣은 원안 u01보다 낫다.

  3. 코드 수정에는 탐색 정지 계열이 가장 강하다

    u24m(탐색 정지 + Concise + 짧은 경로)이 코드 수정 18개 태스크에서 −24%, 품질 경고 0이었다. 2차 실험의 "탐색 턴을 없애는 것이 핵심"이라는 해석은 코드 수정에서 가장 잘 맞는다.

  4. 명세 해석이 필요한 일에서는 "명세를 믿고 확인하지 않는다"가 위험하다

    거짓 성공이 모두 배송비 명세 구현에서 나왔다. 1차 보고서에서 제안한 "모호한 명세" 트랙이 필요하다는 근거가 하나 더 생겼다.

  5. 도구가 적은 일에서는 n09가 이미 충분하다

    도구 없는 수학, 퍼즐, 리팩터에서는 어떤 가설도 n09를 확실히 넘지 못했다. 사전 맥락 원안은 오히려 출력을 늘렸다. 줄일 탐색 턴이 없는 일에는 이 계열의 가설이 쓸모가 없다.

한계

유형별 결론의 근거 크기는 유형마다 다르다

고정 태스크는 1개 × 3회

수학, 퍼즐, 리팩터, 버그 수정, 큰 파일, 기능 추가, 고정 데이터 분석은 태스크가 하나씩이다. 이 칸들의 판정은 그 태스크 하나에 대한 것이고, 유형 전체로 일반화하기 어렵다.

→ 유형별 생성기를 늘린다

유형별 판정은 여러 번 비교한 결과다

조건 4개 × 유형 11개를 비교했으므로 우연히 통과하는 칸이 나올 수 있다. 생성기 유형(문제 16개)의 결과가 가장 믿을 만하다.

→ 라우팅안을 새 문제로 한 번 더 확인

라우팅을 직접 실험하지는 않았다

영역별 권장 설정을 실제로 바꿔 끼우는 라우터는 만들지 않았다. 일의 종류를 어떻게 판별할지가 실사용의 숙제다.

→ 프로젝트별 CLAUDE.md로 나누는 방식부터

정확도 천장은 여전하다

대부분의 실행이 만점이라, 이번에 잡힌 품질 문제는 400건 중 1건 수준의 미세한 실수다. 더 어려운 일에서는 위험이 커질 수 있다.
